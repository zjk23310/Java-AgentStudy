# 黑马点评登录流程复盘

> 基于当前 `hm-dianping` 源码，2026 年 10 月 15 日。本文说明代码实际执行的流程；未启动服务或运行登录接口测试。这里的 token 是服务端 Redis 会话索引，**不是 JWT**。

## 一 核心结论

用户先用手机号获取 6 位验证码；验证码以手机号为键存入 Redis，2 分钟后过期。用户提交手机号和验证码后，服务端查询或创建用户，生成 UUID token，将精简的 `UserDTO` 存入 Redis Hash 并设置 30 分钟有效期。之后客户端把 token 放入 `authorization` 请求头；第一个拦截器读取 Redis 用户并刷新有效期，第二个拦截器判断受保护接口是否已登录。

```text

POST /user/code(phone)

→ 校验手机号 → Redis SET login:code:{phone} = 6位码，TTL 2分钟

→ 当前代码仅在日志打印验证码，没有发送真实短信

POST /user/login({phone, code})

→ Redis GET 验证码 → MySQL 查询/创建用户

→ UUID token → Redis Hash login:token:{token} = UserDTO，TTL 30分钟

→ 返回 token

后续请求：authorization: {token}

→ RefreshTokenInterceptor（order 0）：读取 Redis、写 UserHolder、续期

→ LoginInInterceptor（order 1）：受保护接口检查 UserHolder

→ Controller / Service

→ 当前代码未清理 UserHolder 的 ThreadLocal

```

## 二 按源码走一遍请求

### 1 获取验证码

[UserController](hm-dianping/src/main/java/com/hmdp/controller/UserController.java) 的 `POST /user/code` 调用 [UserServiceImpl.sendCode](hm-dianping/src/main/java/com/hmdp/service/impl/UserServiceImpl.java)。服务先用正则校验手机号，再生成 6 位数字验证码，执行 `SET login:code:{phone} {code} EX 120` 的等价 Redis 操作。TTL 常量在 [RedisConstants](hm-dianping/src/main/java/com/hmdp/utils/RedisConstants.java)。接口返回 `Result.ok()`。

**准确表述：** 代码通过 `log.debug` 输出验证码，尚未接入短信平台。`HttpSession` 虽作为方法参数传入，但 `sendCode` 没有使用它。

### 2 校验验证码并完成登录或注册

`POST /user/login` 接收 `LoginFormDTO`，其中定义了 `phone`、`code`、`password`，但当前 [login 实现](hm-dianping/src/main/java/com/hmdp/service/impl/UserServiceImpl.java)只使用手机号和验证码：

1. 再次校验手机号格式。

2. 从 `login:code:{phone}` 读取验证码，与提交值比较；不存在或不匹配则失败。

3. 用手机号查询 `tb_user`；不存在则创建用户。SQL 脚本对手机号有唯一索引，见 [hmdp.sql](hm-dianping/src/main/resources/db/hmdp.sql)。

4. 把用户的 `id`、昵称和头像复制到 [UserDTO](hm-dianping/src/main/java/com/hmdp/dto/UserDTO.java)，避免把完整用户实体放入登录态。

5. 生成 UUID 字符串作为 token，把 `UserDTO` 字段转为字符串写入 Redis Hash `login:token:{token}`，有效期 30 分钟。

6. 返回 token。代码还调用 `session.setAttribute("userDto", userDTO)`，但后续认证实际从 Redis 读取，并没有使用该 Session 字段。

**关键区分：** 客户端拿到的是随机 token；用户资料在服务端 Redis。它与“把用户声明和签名编码在 JWT 中”是两种不同设计。

### 3 后续请求如何识别用户

[MvcConfig](hm-dianping/src/main/java/com/hmdp/config/MvcConfig.java) 注册两个拦截器：

| 顺序 | 拦截器 | 当前职责 |

| --- | --- | --- |

| `order(0)` | [RefreshTokenInterceptor](hm-dianping/src/main/java/com/hmdp/utils/RefreshTokenInterceptor.java) | 对所有请求尝试读取原始 `authorization` 头。若 Redis Hash 存在，则还原 `UserDTO`，放入 [UserHolder](hm-dianping/src/main/java/com/hmdp/utils/UserHolder.java) 的 ThreadLocal，并把 token TTL 刷回 30 分钟。没有 token 或查不到用户时，直接放行。 |

| `order(1)` | [LoginInInterceptor](hm-dianping/src/main/java/com/hmdp/utils/LoginInInterceptor.java) | 对受保护接口检查 `UserHolder.getUser()` 是否为 null；为空则返回 `false`，不再执行 Controller。 `/user/code`、`/user/login` 等路径被排除。 |

这两个拦截器分工的目的：**先恢复当前请求的用户身份，再决定当前接口是否要求登录**。例如 `GET /user/me` 经认证后直接返回 `UserHolder` 中的 `UserDTO`。公开接口也会经过续期拦截器，因此携带有效 token 访问公开接口同样会续期。

### 4 现有缓存键

| Redis 键 | 类型 | 内容 | 过期 |

| --- | --- | --- | --- |

| `login:code:{phone}` | String | 6 位验证码 | 2 分钟 |

| `login:token:{token}` | Hash | `UserDTO` 的 id、昵称、头像 | 登录后 30 分钟；携带有效 token 的请求会刷新到 30 分钟 |

客户端当前需传**原始 token** 到 `authorization` 请求头；拦截器没有解析 `Bearer ` 前缀。切换成常见 Bearer 格式时，服务端也必须同步支持解析。

## 三 当前实现的风险与建议顺序

| 优先级 | 代码现状与影响 | 最小改进与验证 |

| --- | --- | --- |

| P0 | `UserHolder` 有 `removeUser()`，但两个拦截器的 `afterCompletion` 都为空。Servlet 线程复用时，上一请求的用户可能残留；无 token 的后续请求也可能被误判为已登录。 | 在先执行且覆盖全部请求的续期拦截器完成回调中清理 ThreadLocal；测试同一线程先访问有 token 请求，再访问无 token 的受保护接口。 |

| P0 | `LoginInInterceptor` 返回 `false` 时未设置 401 状态码或错误体。 | 明确返回 HTTP 401，并用接口测试核对响应。 |

| P0 | [MvcConfig](hm-dianping/src/main/java/com/hmdp/config/MvcConfig.java) 将 `/upload/**` 整体排除登录校验；[UploadController](hm-dianping/src/main/java/com/hmdp/controller/UploadController.java) 中包含上传和删除操作。 | 逐个界定公开与受保护接口；对上传、删除增加登录和资源权限校验。 |

| P1 | 验证码校验成功后没有删除，2 分钟内可以再次使用；发送和校验都没有频率／错误次数限制。 | 登录成功后删除验证码；按手机号及来源做限流和失败次数控制，覆盖重复提交测试。 |

| P1 | 验证码仅打印在日志；`logout` 返回“功能未完成”。 | 接入短信服务前不要宣称已发送短信；登出时删除 Redis token 并测试旧 token 失效。 |

| P1 | 认证依赖 Redis token，同时仍创建并写入 `HttpSession`。 | 确认前端没有依赖 Session 后移除多余的 Session 参数和写入，保持单一登录态来源。 |

| P2 | 每个有效请求都执行 Redis `EXPIRE`。 | 当前流量下先保留简单实现；只有观测到写入压力时，再考虑接近过期才续期。 |

**并发注册补充：** `tb_user.phone` 唯一索引能防数据库出现两个相同手机号用户，但“查询不存在 → 插入”并非原子流程。若并发登录同一新手机号，需要正确处理唯一键冲突并重新查询，不要仅靠先查后插。

## 四 适合留下的测试证据

1. **验证码：** 错误手机号、错误验证码、已过期验证码；成功登录后重复使用同一验证码应失败（完成改造后）。

2. **登录：** 旧用户登录、新用户注册登录、同一手机号并发注册；验证数据库唯一索引和返回 token。

3. **鉴权：** 无 token、无效 token、有效 token；验证 `GET /user/me` 及未登录状态的 HTTP 401。

4. **隔离：** 在线程池复用条件下，先以 A 用户请求，再发送不带 token 或 B 用户请求，确认身份不会串线。

5. **生命周期：** 有效请求刷新 TTL；登出后旧 token 不能继续访问（完成登出改造后）。

## 五 面试时可以这样讲

> 项目使用手机号验证码登录。验证码以手机号为键存 Redis，设置 2 分钟有效期；校验通过后查询或创建用户，生成随机 token，把精简用户信息存 Redis Hash，并设置 30 分钟过期时间。后续请求由第一个拦截器根据 token 恢复用户并续期，再由第二个拦截器检查受保护接口是否已登录。用户信息只在请求线程的 ThreadLocal 中暂存，请求结束需要清理，防止线程复用导致身份串线。这个实现属于 Redis 管理的 token 会话，并不是 JWT。

如果尚未修复 ThreadLocal 清理、401、验证码复用和登出，面试时应表述为**发现的问题与改造计划**，不要把计划写成已完成的安全设计。

### 常见追问

- **为何存 `UserDTO` 而不是完整 User？** 登录鉴权只需要少量公开字段，减少 Redis 存储和敏感字段暴露。

- **为何把 token 放 Redis？** 服务器可按 token 查询用户并控制有效期与主动失效；代价是每次鉴权要访问 Redis。

- **为什么两个拦截器有先后顺序？** 第一个负责恢复用户身份，第二个才有数据可做登录校验；公开接口只跳过第二个。

- **ThreadLocal 可以代替 Redis 吗？** 不可以。ThreadLocal 只服务当前请求线程；Redis 才跨请求保存登录态。

- **登录成功是否保证以后一直已登录？** 不能。token 会过期、被删除或 Redis 不可用；服务端要给出明确的未授权响应。

## 六 复盘边界

本文只分析当前工作区代码，没有修改实现，也没有运行 MySQL、Redis 或接口测试。项目依赖和拦截器注册以本地源码为准；任何“安全上线”“高并发登录”或响应时间结论都需另行测试证明。
