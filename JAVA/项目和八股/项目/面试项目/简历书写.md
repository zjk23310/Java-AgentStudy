# 简历书写

## 文件解析 
面向 PDF/DOCX/TXT 等多格式简历上传场景，基于 Apache Tika 实现文档解析，并通过 MIME + 扩展名校验、文本清洗和 SHA-256 哈希去重，减少非法文件、脏文本和重复 AI 调用。

简历分析和知识库上传的第一步都是文档解析。如果这里输入质量差，后面的 AI 分析和向量检索都会受影响。所以对文件进行解析得到良好的输入字符串很重要，所以把文件处理拆成校验、解析、清洗、去重四步来确保输入的质量
以上传简历为例，在上传简历前，首先对简历文件的大小进行校验，校验通过则继续检验类型是否支持（这里类型校验并不是只使用扩展名检验，因为用户可能将文件后缀更改。使用MIME更加可靠，但并不是绝对安全，所以采用双重校验提高拦截率），如果类型支持则根据文件的哈希值来确定是否之前已经传入重复的文档（去重采用的是SHA-256，而非文件名，采用SHA-256去重能够确保文件内容相同则文件哈希相同从而减少重复文件的上传，减少存储、API额度等资源的浪费），如果之前传入过就直接获取历史简历的解析结果并返回。如果之前未传入则解析并清洗简历的文本。清洗文本可以分为两步，第一步使用正则表达式将文中的一些无关信息，如图像的url、文件的路径等清除。第二步则是对文本的格式进行处理，比如将多行换行改为1行，去除行尾的制表符或空格。解析完成之后会将原文件存入RustFS。之后将RustFS文件的url还有文本内容存入到数据库。存入数据库之后将简历分析的任务放入到响应的Redis Stream中异步处理。最后返回结果

## Redis Stream
针对简历分析、知识库向量化、面试评估等 LLM 任务耗时较长的问题，基于 Redis Stream 封装 Producer/Consumer 模板，实现任务异步化、状态流转和最多 3 次失败重试，上传接口可快速返回任务状态。

业务存在的问题：简历分析、知识库向量化、面试评估都要调用 LLM 或 Embedding 模型，耗时不可控。如果用户上传简历后接口一直等模型返回，体验会很差，也容易导致连接超时。所以我把耗时任务从请求链路里拆出去。项目里面创建了Consumer和Producer的基类。Producer基类中统一负责发送信息，Consumer基类中统一创建消费者、轮询消息、处理业务并ACK和失败重试。不同的业务分别实现继承并具体实现对应的方法。这里以简历分析为例，上面已经提到了在上传简历的时候会向Redis Stream中存入对应的任务。具体实现就是Resume模块中具体实现了AnalyzeStreamProducer和Consumer。AnalyzeProducer会调用基类方法将resumeId封装并分发消息。Consumer消费者则轮询并处理消息。其重写了处理业务的逻辑：处理时会根据resumeId获取数据库中的简历文本，如果数据库中文本不存在就从RustFS中下载恢复简历文本，成功则对简历进行评分。Consumer 消费到消息后先把业务实体标记为 PROCESSING。业务处理成功后改为 COMPLETED 并 ACK。异常时读取消息里的 retryCount，如果没超过最大次数，就重新投递一条带新 retryCount 的消息；超过次数就标记 FAILED，并记录错误摘要，最后 ACK 当前消息，避免同一条消息一直卡住。
