# 堆空间基本结构
现在收集器都采用**分代垃圾收集算法**
JDK7和以前，GC按下面三部分介绍：
1.新生代、2.老生代、3.永久代（方法区的实现）
JDK8移除了永久代，类元数据改为存放在使用本地内存的元空间中
# 内存分配和回收原则
## 对象优先在Eden区分配
大多情况，对象在新生代中Eden区分配，如果没有足够空间分配会进行一次Minor GC
执行Minor GC后仍无法存入Survivor空间，就要通过**分配担保机制**把新生代对象提前转移到老年代。老年代足够放则不会触发Full GC。如果执行Minor GC后，后续分配对象可以存放Eden区就可以直接在Eden区分配内存
## 大对象直接进入老年代
这是一种优化策略，可以避免大对象放入新生代而减少新生代的垃圾回收频率和成本
垃圾回收的示例：
```
- G1 垃圾回收器把大小达到或超过 Region 一半的对象视为 Humongous Object，并直接分配到属于老年代的连续 Humongous Region 中。Region 大小可通过 `-XX:G1HeapRegionSize` 设置。
- 其他收集器是否以及在什么条件下把大对象直接分配到老年代，取决于具体收集器和 JDK 版本，不能用一个通用阈值概括。
```
## 长期存活的对象进入老年代
虚拟机次啊用分代收集则给每个对象一个对象年龄计数器
对象大多情况下在Eden区域分配，熬过Minor GC后会进入到Survivor区（s0或s1），之后每熬过一次Minor GC都会导致年龄增加一岁，增加到阈值后会进入老年区
## 主要进行gc的区域
针对HotSpot VM，其里面的GC 准确分类只有两类
**部分收集**（Partial GC）主要包括：新生代收集、老年代收集、混合收集
**整堆收集**（Mixed GC）对整个Java对进行收集，是否回收方法区中的类元数据则取决于收集器、JDK版本、类卸载条件等
## 空间分配担保
确保Minor GC前老年代本身还有容纳新生代虽有对象的剩余空间
# 死亡对象的判断方法
在回收垃圾之前肯定要判断何时对象才算作死亡
## 引用计数法
对象添加一个引用计数器
有地方引用则加一。引用失效则减一，为0则该对象不可能再次被使用
这个方法比较简单，但是无法解决循环引用的问题
obj1引用obj2，obj2引用obj1
## 可达性分析算法
从一系列成为GC Roots的对象作为起点，向下搜索，节点所走过的路径成为引用链，若一个对象到GC Roots没有任何引用链相连，则证明此对象不可用
有很多对象可以作为GC Roots
- 虚拟机栈（栈帧中的局部变量表）中引用的对象
- 本地方法栈（Native 方法）中引用的对象
- 方法区中类静态属性引用的对象
- 方法区中常量引用的对象
- 所有被同步锁持有的对象
- JNI（Java Native Interface）引用的对象
**对象可以被回收并不代表着一定会被回收**
这有关finalize方法，对于这个方法我知之甚少，它是一个糟糕的设计
## 引用类型总结
1.2之前如果 reference 类型的数据存储的数值代表的是另一块内存的起始地址，就称这块内存代表一个引用。
Java 对引用的概念进行了扩充，将引用分为强引用、软引用、弱引用、虚引用四种（引用强度逐渐减弱）。强引用就是程序代码中普遍存在的普通引用赋值，软引用、弱引用、虚引用在 JDK 中定义的类分别是 `SoftReference`、`WeakReference`、`PhantomReference`。
### 强引用
实际上就是程序代码中普遍存在的引用，如果存在强引用就算空间不足抛出异常也不会随意回收强引用对象
### 软引用
如果一个对象只具有软引用，那就类似于**可有可无的生活用品**


C++中主要通过delete还有new来手动创建、删除堆内存，JAVA则想要实现自动管理
**GC**：Garbage Collection，垃圾回收。
**垃圾对象**：不再能够通过有效引用链访问、可以被回收的对象。
**GC** 不等于立即释放内存：对象变得不可达后，JVM 可以在之后的垃圾回收过程中回收它。

JVM 会从一组特殊的引用出发，寻找它们能够访问到的对象就是[[GC_ROOTS]]

java垃圾回收主要有三种方式：
1. 标记清除算法
2. 复制算法
3. 标记压缩算法

标记清除算法会残生大量的碎片，标记压缩也就是标记整理，会整理来减少内存碎片

> java代码举例
```java
import java.util.ArrayList;
import java.util.List;
public class GCDemo {
    // 保存长期存活的对象
    private static final List<byte[]> survivors =
            new ArrayList<>();
    public static void main(String[] args) {
        // 创建一个长期存活的对象
        byte[] longLived = new byte[1024 * 1024];
        survivors.add(longLived);
        // 不断创建临时对象
        for (int i = 0; i < 10000; i++) {
            byte[] temp = new byte[1024 * 100];
        }
        System.out.println("程序结束");
    }
}
```
longLived是一个长期的对象，temp是临时对象每次循环都会创建一个约 100 KB 的数组。这些临时数组在不再被使用后，就可能成为垃圾回收对象。随着不断分配内存，Eden 区可能被填满，从而触发 Young GC。
假设此时：
- longLived 仍然存活。
- 大量 temp 数组已经不可达。
垃圾回收器会回收死亡对象，并根据收集器的策略，将 longLived 复制到 Survivor 区或直接晋升到老年代。
这就是所谓的“对象被复制”。
注意：这段代码只是为了说明对象生命周期，不保证一定触发 15 次 Young GC，也不保证 longLived 一定经历 Survivor 区。

在 JVM 分代垃圾回收机制中，新对象通常分配在年轻代 Eden 区。
当年轻代发生垃圾回收时，垃圾回收器会识别仍然存活的对象，并采用复制算法将它们移动到 Survivor 区或者晋升到老年代。
对象每经历一次符合条件的年轻代回收并存活，其年龄通常会增加。当年龄达到晋升阈值时，就可能进入老年代。
经典 HotSpot 分代 GC 中常见的最大年龄阈值是 15，但对象可能由于 Survivor 空间不足、动态年龄判定等原因提前晋升。
复制算法的优势是能够快速回收大量短命对象，并减少内存碎片。

>扩展部分：
1. Minor GC、Major GC、Full GC
2. 内存泄漏：程序在运行过程中不再使用的对象仍然被引用，无法被垃圾回收，导致可用内存减少
   原因有：
    静态集合：使用静态数据结构存储对象，没有进行清理。
    事件监听：未取消对事件源的监听，导致对象持续被引用。
    线程：未停止的线程可能持有对象引用，无法被回收。
3. 内存溢出：JVM申请内存时无法找到足够的内存，引发OutOfMemoryError
   原因：
    堆内存溢出：代码中出现大对象分配或者是内存泄漏时，多次GC也没有足够的内存空间。
    栈溢出：代码中出现递归调用，压栈过深或者无法扩展栈空间时出现。
    元空间溢出：系统的代码过多或加载的类文件过多，导致元空间内存占用大。
