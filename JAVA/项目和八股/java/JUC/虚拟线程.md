虚拟线程的核心目标：以极低的成本支撑海量并发阻塞任务，提升系统整体吞吐

 与平台线程的关键区别

| 维度        | 平台线程            | 虚拟线程            |
| --------- | --------------- | --------------- |
| 管理方       | 操作系统内核          | JVM（用户空间）       |
| 与 OS 线程关系 | 1:1，独占          | M:N，动态复用载体线程    |
| 栈内存       | 固定（通常约 1MB）     | 在堆上动态分配，初始仅几百字节 |
| 阻塞行为      | 阻塞时占住整个 OS 线程   | 阻塞时自动卸载，释放载体线程  |
| 数量级       | 受 OS 与内存限制，通常数千 | 可达百万级           |
虚拟线程的**单个任务执行速度并不比平台线程快**。它的价值在于：当大量任务大部分时间都在等待 I/O 时，系统不必再为“等待”付出昂贵的线程资源成本，从而把同样的硬件用于承载更多的并发任务。

虚拟线程**不是**“更快的线程”，它优化的是“等待”而非“执行”。只有在任务存在大量阻塞等待时，它的吞吐量优势才会体现；对于极快的、几乎不阻塞的调用，平台线程的表现可能相当甚至更好。

这里有两个实践的要点：
1.不要池化虚拟线程。因为传统线程池存在的根本理由就是平台线程创建的成本很高，需要复用。虚拟线程的创建很廉价，池化反而会引入不必要的锁竞争和管理开销
2.注意pinning问题，这某些情况下，虚拟线程在阻塞的时候无法被卸载，会持续占用载体线程，导致并发能力退化为载体线程的数量在 。JDK 21 中，在 `synchronized` 块或方法内部发生阻塞是导致 Pinning 的最常见原因；执行 JNI 本地方法调用也可能触发
