# Select* 查询
`SELECT *` 本身**不会直接导致索引失效**。它是一种”非覆盖索引”查询，如果 `WHERE` 条件命中了索引，索引依然会被初步考虑
从回表成本决策，如果查询需要的字段不在索引树要回表，如果占总表的占比比较大，则决策其可能认为全表的顺序IO反而更快，所以就不会使用索引。因此可以建立适当的联合索引，这样可以避免回表
# 违背最左前缀原则
最左匹配是指使用联合索引时，MySQL会根据索引中的字段顺序，从左到右一次匹配查询条件中的字段
如果使用了范围查询会导致这个字段和之前的字段能够正常匹配，后面的字段无法被利用。但是后面的字段会降级使用索引下推，在范围扫描的过程中直接进行条件过滤
索引跳跃扫描？
# 在索引列上进行计算、函数、类型转换
B+Tree存储的是字段的原始值，一旦在where条件中对索引列应用了函数或算数运算该列的逻辑就会发生改变。导致有序性被破坏，只能够被迫进行全表扫描
虽然有函数索引可以针对计算后的值键索引，但是泛用性不强
# Like模糊匹配
Like查询必须要以具体字符开头才能够使用索引的有序性。前缀通配符破坏了B+树的有序性。如果必须进行前缀模糊匹配，应当使用对应的覆盖索引，对于核心业务的模糊查询可以考虑使用ElasticSearch
# OR连接与Index Merge
在OR连接的字段中，任何一列没有索引，MySQL就会放弃所有索引转而执行全表扫描
**Index Merge**:如果OR两边都有索引的话（5.1+）可能会触发索引合并。分别扫描两个索引之后取并集。如果索引过滤后的数据量依旧很大，则仍然可能使用全表扫描
在实际使用时应当将OR改为union，只有确定结果集不重复的时候才能够使用union all
# IN/NOT IN
in列表长度小于阈值的时候会使用Index Dive，如果in长度超过阈值则基于index_statistics。会选择全表扫描
not in 对于常量列表需要进行全表扫描，因为不确定B+树哪些数据不在not in列表中。
可以使用not exists或者left join/is null，他们的性能更好并且语义清晰
## 短路求值
短路求值是针对每个用户各自的子查询而言的，不是对整个外层查询而言的
# 隐式类型转换
只有当转换发生在索引列的时候索引才会失效。当字符串与数字进行比较时，MySQL会将字符串转换为浮点数进行比较。对索引进行隐式类型转换相当于使用了不可逆的函数，破坏了B+树的结构
- `int_col = '123'` 会被转换为 `int_col = CAST('123' AS DOUBLE)`，转换发生在常量侧，不影响索引使用。

# ORDER BY
排序优化缺陷
就算where条件比较精准，但order by处理不好也会出现慢查询
以下情况会出现慢查询：排序字段不在索引中；排序的顺序与索引字段的顺序不一样；where和order by使用不同的索引；排序列包含select \*中的非索引列
针对这些情况，可以使用下面的一些决策：使用覆盖索引来同时满足where条件和order by。比如创建了索引之后，where查询使用索引可以缩小范围，orderby可以根据后面的索引排序。
同时可以调整索引的顺序来适应order by
